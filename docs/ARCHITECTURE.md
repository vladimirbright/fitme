# Fitme — Architecture

Status: design, pre-implementation. Audience: an AI coding agent (the "executor") and the
operator. Read `AGENTS.md` first — it overrides anything here. Build order and acceptance
criteria are in `docs/IMPLEMENTATION_PLAN.md`.

## 0. What this is

Fitme is a **single-user, self-hosted training plan generator and training log**:

- a Telegram bot, the main input tool: setup questionnaire, plan generation, guided workouts,
  result logging;
- a small website: plans, past trainings, progress charts.

Plans are generated by an LLM, and deterministic guards check them before anyone sees them.
Fitme is not a trainer, coach or medical tool, and all user-facing copy must say that plans
are AI-generated (AGENTS.md §3).

### 0.1 Single-user posture (hard constraint)

One instance serves **exactly one person: the operator**. See `docs/adr/0002-single-user.md`.

- No invites, waiting list, sign-up, marketing page, or admin role.
- The operator binds their Telegram account once with an activation code from the CLI
  (§6.1). After that, the bot ignores every other Telegram account.
- The schema keeps a `user_id` foreign key everywhere so the data stays cleanly separated
  and exportable. The **application enforces at most one user row**.
- Multi-user support changes the posture (AGENTS.md §8). Do not build it.

| Data files | TOML (stdlib `tomllib`) | Exercise catalog, locales, model prices. Needs no YAML dependency. Why files and not SQLite: §4.8. |

| Tests | `pytest`, `pytest-asyncio` | The LLM is always faked in tests (`pydantic_ai.models.test` / `FunctionModel`). |
| Lint / types | `ruff`, `mypy` (strict on `guards/` and `domain/`) | |

Everything else needs a reason. Prefer boring dependencies (AGENTS.md §9).

### 2.1 Dependency direction (enforced by review, optionally by `import-linter`)

```
bot, web, cli  ──►  services  ──►  guards, llm, db  ──►  domain
                                   guards ──► domain only
```

- `guards/` imports **only** `domain/` and the stdlib. It never imports `llm/`, `db/`,
  pydantic-ai, aiogram or FastAPI.
- `bot/` and `web/` never call `llm/` or `db/` directly. They call `services/`.
- SQL text exists only in `db/controllers/`, `db/selectors/` and `db/migrations/*.sql`
  (§4.6).
- Both front-ends use the same services. A plan generated on the web and one generated in
  the bot go through the same code path and the same guards.

## 3. Runtime

One process: `uv run fitme serve`.

- It starts the aiogram dispatcher (long polling) and uvicorn (FastAPI) as tasks in one
  event loop.
- A background task runs retention every 24 hours (§8.4).
- SQLite runs with `journal_mode=WAL`, `foreign_keys=ON` and `busy_timeout=5000`.
- Workout state lives in the DB, not in memory, so a restart during a workout resumes where
  it stopped (§6.5).

Reference deployment: **Docker Compose** with a small `python:3.13-alpine` image, running as
non-root with a read-only root filesystem and the SQLite file on a named volume. An optional
Caddy service provides TLS. Backups use `fitme backup` (the sqlite3 online backup API) from
host cron. See M10.

## 4. Data model

Tables are grouped by concern (AGENTS.md §5). The **identity**, **health** and **derived**
groups must stay separate: health and derived tables never store Telegram identifiers.

### 4.1 Identity & auth

| Table | Columns | Notes |
|---|---|---|
| `users` | `id` PK, `language`, `timezone` (IANA), `created_at` | App enforces ≤1 row. |
| `telegram_accounts` | `id` PK, `user_id` FK **unique**, `telegram_user_id` **unique**, `chat_id`, `linked_at` | 1:1 link. Other identity types can get their own table later. |
| `activation_codes` | `id`, `code_hash`, `expires_at`, `used_at` | Created by `fitme activate`. |
| `login_codes` | `id`, `user_id`, `code_hash`, `created_at` (migration 0004), `expires_at`, `attempts`, `used_at` | Website OTP. |
| `web_sessions` | `id_hash` PK, `user_id`, `created_at`, `last_seen_at`, `expires_at` | Server-side session. The cookie holds only the random id. |

Hash every code and session id with SHA-256 before storing it. Never store them in
plaintext.

### 4.2 Health & self-reports

| Table | Columns | Notes |
|---|---|---|
| `profiles` | `user_id` PK, `age_bucket`, `weight_bucket`, `experience`, `barbell_experience`, `preferences` (JSON list of enum), `location`, `equipment` (JSON list of enum), `sessions_per_week`, `session_minutes`, `focus`, `completed_at`, `updated_at` | Enums only. Buckets, not exact values. |
| `screening_flags` | `user_id`, `flag` (enum), `value` (`yes`/`no`/`unknown`), `clearance` (`yes`/`no`/null), `answered_at` | One row per flag. **These gate exercise selection.** |
| `screening_notes` | `user_id`, `text`, `created_at` | Optional free text for "other". **Never sent to the LLM.** Shown back to the user only. |
| `health_holds` | `id`, `user_id`, `reason` (enum: `stop_word`, `checkin_pain`, `llm_safety_signal`, `precheck_yes`, `pain_button`), `source_session_id` (nullable, `ON DELETE SET NULL`), `created_at`, `cleared_at` | An open hold blocks `/plan` and `/train` until cleared (§6.6). |
| `workout_sessions` | `id`, `user_id`, `plan_version_id` (nullable since migration 0007: imported sessions belong to no plan), `workout_key`, `import_hash` (nullable, unique per user; migration 0006), `status` (`draft`,`confirmed`,`in_progress`,`completed`,`aborted`,`halted`), `current_block`, `started_at`, `finished_at`, `halt_reason` | Performed trainings. |
| `set_logs` | `id`, `session_id`, `exercise_id`, `set_index`, `planned_load_kg`, `planned_reps_min`, `planned_reps_max`, `actual_load_kg`, `actual_reps` (nullable), `skipped` (0/1), `rpe` (nullable), `source` (`button`,`free_text`,`web`,`import`), `created_at` | **Source of truth for history and historical max.** One row per **prescribed** set, created when the block is sent. A set not performed is `skipped=1` with `actual_*` NULL, so missing sets are visible. A set done beyond the prescription is its own row with `extra_for_block`/`extra_for_item` set, the prescribed `planned_load_kg` and no planned reps (ADR 0012); progression ignores it. |
| `checkins` | `id`, `user_id`, `session_id` (nullable, `ON DELETE SET NULL`), `question_key` (e.g. `area:lower_back`), `answer` (`fine`,`worse`,`pain`,`unknown`), `asked_at`, `answered_at` | Rows are created as `unknown` and updated only by an explicit answer. |
| `chat_messages` | `id`, `user_id`, `session_id` nullable, `direction`, `text`, `created_at`, `conversation_id` nullable | Raw text, the owner's (`in`) and the assistant's replies (`out`). **Deleted after `FITME_CHAT_RETENTION_DAYS`.** |
| `conversations` | `id`, `user_id`, `kind` (`planning`/`training`), `plan_id`, `workout_session_id`, `draft_decision_id`, `status` (`open`/`saved`/`discarded`/`closed`), `started_at`, `updated_at`, `closed_at` | ADR 0004: an assistant session. No text. Closed ones are deleted with their messages. |

Bucket enums:

- `age_bucket`: `18_29`, `30_39`, `40_49`, `50_59`, `60_69`, `70_79`, `80_90`. There is no
  under-18 option (AGENTS.md §4).
- `weight_bucket`: `30_39` … `190_200` in 10 kg steps (17 values).

Canonical enum values. Schema CHECKs, domain enums, the catalog and locales all use these
exact strings:

- `experience`: `none`, `lt_6m`, `6m_2y`, `2y_5y`, `gt_5y`.
- `barbell_experience`: `yes`, `some`, `no`.
- `preferences`: `weight_training`, `full_body`, `split`, `bodyweight`, `conditioning`,
  `mobility`.
- `focus`: `strength`, `muscle`, `general_fitness`, `conditioning`.
- `location`: `public_gym`, `studio_gym`, `home_equipment`, `apartment_no_equipment`,
  `outdoor`.
- `equipment`: `dumbbells`, `barbell`, `rack`, `bench`, `pull_up_bar`, `kettlebell`,
  `resistance_bands`, `machine`, `cable`. `machine` and `cable` are gym-only: gym
  locations have them by default, and the home-equipment question doesn't offer them.
- `pattern` (catalog): `squat`, `hinge`, `horizontal_push`, `horizontal_pull`,
  `vertical_push`, `vertical_pull`, `core`, `mobility`, `conditioning`, `accessory`.
- `screening_flags.flag`:
  - Red flags: `heart_condition`, `chest_discomfort`, `dizziness_fainting`,
    `high_blood_pressure`, `recent_surgery`, `pregnant`, `other_condition_limits`.
  - Areas: `neck_injury_current`, `shoulder_injury_current`, `elbow_wrist_injury_current`,
    `lower_back_injury_current`, `hip_injury_current`, `knee_injury_current`,
    `ankle_injury_current`, `hernia`.
  - Free text: `other_unlisted`.
- `chat_messages.direction`: `in`, `out`.

**Timestamps.** All timestamp columns are TEXT in one format: UTC
`YYYY-MM-DDTHH:MM:SS.ffffffZ`, always with 6 fractional digits, so lexical order equals
time order. Only `fitme.clock` produces them. Controllers default to `clock.utc_now()` and
never accept free-form strings from callers.

### 4.3 Derived output

| Table | Columns | Notes |
|---|---|---|
| `plans` | `id`, `user_id`, `name`, `is_default`, `status`, `created_at` | At most one `is_default` per user. **All plans are equal** (operator decision, 2026-09-28). There is no archived state: every plan can be viewed, edited and revised, trained from at any time, and marked as default, in the bot and on the website. The `status` column keeps its old CHECK for schema compatibility, but only `active` is written, and migration 0007 turns any `archived` row into `active`. **Any plan can be deleted** (web edit page and bot `/plan`, after a confirm step). Deleting a plan keeps its trainings: they are detached (`plan_version_id` → NULL) and stay in the log. Draft, confirmed or in-progress sessions on the plan are aborted first. The plan's versions and row are removed; decisions are kept. If it was the default, the most recently created remaining plan becomes the default. A `decision(kind=user_edit, user_report={"action":"delete_plan","plan_id":…})` is logged. Deleting a plan never raises what the guards allow, because history max, the weekly cap and applied lifts come from logs and decisions, not plans. |
| `plan_versions` | `id`, `plan_id`, `version`, `body` (JSON, `domain.Plan`), `origin` (`llm`,`progression`,`user_edit`,`import`), `decision_id`, `created_at` | **Immutable.** Every change creates a new version. |
| `decisions` | `id`, `user_id`, `kind`, `prompt_template`, `prompt_version`, `model`, `content_version` (§4.8), `llm_input` (JSON, pseudonymized, exactly as sent), `user_report` (JSON), `proposal` (JSON), `load_changes` (JSON array of `domain.LoadChange {exercise_id, from_kg, to_kg}`, default `[]`), `guards_fired` (JSON list of `{rule, verdict, detail}`), `created_at` | **Append-only.** AGENTS.md §6. |
| `decision_outcomes` | `id`, `decision_id`, `outcome` (JSON: what the user actually did), `created_at` | Append-only. Lets the log stay immutable when the outcome arrives later. |
| `llm_calls` | `id`, `decision_id` nullable, `purpose`, `model`, `input_tokens`, `output_tokens`, `cost_estimate_usd` nullable, `latency_ms`, `ok`, `created_at` | Feeds `/system`. No prompt content here. |

`decisions.kind` values: `plan_generate`, `plan_revise`, `session_adjust`,
`result_parse` (results logged during a workout; since ADR 0013 written only by the
assistant, `event=assistant_log`), `progression`, `session_halt`, `hold_clear`, `refusal`, `user_edit`,
`session_delete`, `history_import`, `plan_confirm`, `plan_import`.

**Load changes count once, when applied.** Draft decisions (`plan_generate`/`plan_revise`/`plan_import`)
show their proposed changes inside `proposal`, but their `load_changes` column is `[]`.
The `plan_confirm` decision written inside the confirm transaction carries the
`load_changes`, computed against the **confirm-time** reference. The same holds for every
other applying decision (`progression`, `session_adjust` when applied, `user_edit`,
`history_import` = none).

Enforce immutability in the controller layer: `plan_versions`, `decisions` and
`decision_outcomes` have no update or delete methods, except the full-account delete (§8.3).

### 4.4 Exercise catalog (`src/fitme/catalog/exercises/`)

The system may only prescribe catalog exercises. Loaded at startup and validated with a
pydantic model. There is no DB table: `set_logs.exercise_id` references the catalog `id`.
One file per exercise, `exercises/<range>/<id>.toml`, ranged by the id's first letter
(`a-c`, `d-f`, …); the file's top-level keys are the exercise (ADR 0006). Shown below as one
file, `exercises/a-c/barbell_back_squat.toml`:

```toml
id = "barbell_back_squat"
names = { en = "Barbell back squat", ru = "Приседания со штангой на спине" }
kind = "compound"                    # compound | isolation | bodyweight | cardio | mobility
equipment = ["barbell", "rack"]
locations = ["public_gym", "studio_gym"]
loads_areas = ["knee", "lower_back", "hip"]   # used by screening + check-in gating
contraindicated_by = ["knee_injury_current", "lower_back_injury_current", "hernia"]
increment_kg = 2.5
start = { kind = "kg", kg = 20.0 }   # conservative calibration start: empty bar
instructions = { en = "...", ru = "..." }  # vetted text; shown during training
```

Catalog invariants, enforced by `fitme catalog check` and tests:

- **Contraindications cover loaded areas:** `contraindicated_by ⊇ {<area>_injury_current
  for a in loads_areas}` for every exercise. Any exception is an explicit, commented
  `contraindication_exceptions` entry that has been reviewed.
- **Honest patterns:** an exercise's `pattern` is what it actually is. Coverage rules adapt
  per location; the data is never mislabeled to satisfy them. Required patterns per
  location: all primary patterns, except `apartment_no_equipment`, which does not require
  `vertical_pull` (that needs a bar; plans compensate with horizontal pulls).
- **Loads are per implement:** each exercise declares `load_unit`: `total` (barbell and
  machine stack), `per_implement` (two dumbbells or kettlebells; kg is for each one, shown
  as "{kg} kg each") or `single_implement` (one dumbbell or kettlebell).
- **Non-kg exercises:** `kg_loadable = false` for cardio machines, band-only exercises, mobility and bodyweight
  conditioning. The guards reject any kg prescription on them, and the engine substitutes
  bodyweight or calibration. Prompts and
  UI copy must say so.
- **Implement steps are real:** e.g. kettlebells step 2 or 4 kg.
- **Safety cues:** barbell rack and bench exercises include a cue to set safety arms. The
  barbell deadlift starts at `calibration`, with the bar at standard height.
- **No internal references** ("A§", "AGENTS") in user-visible names or instructions.

**Level and extended equipment (ADR 0008).** `level = "advanced"` marks advanced gymnastics,
Olympic lifts and similar; `guards.experience` (rule `plan.experience_level`) and
`available_exercises` keep them away from anyone with less than two years of training, and
unknown experience fails closed. `Equipment` also covers EZ/trap bars, a Smith machine, balls,
rollers, plates, dip bars, a plyo box, ropes, a sled, a tire and a sledgehammer;
`GYM_ONLY_EQUIPMENT` lists the ones the home questionnaire doesn't offer.

**Measures and qualities (ADR 0009).** `measures` lists how a set of the exercise is
prescribed (`reps`, `time`, `distance`; the first is the default) and `qualities` what it
directly trains (`strength`, `hypertrophy`, `power`, `rotational_power`, `core_stability`,
`agility`, `muscular_endurance`, `conditioning`, `mobility`). `fitme catalog check` requires
`qualities` on every exercise. ADR 0011: the first quality is what the exercise *mainly*
trains, and with its measure decides how its effort is regulated
(`domain.catalog.intensity_mode`: reps in reserve, speed, carry, pace or none). `specific =
true` marks a narrow technique drill or one variation of a broader activity (left hooks only):
retrieval ranks it after general exercises and the review won't take it as a warm-up.
ADR 0016: `unilateral = true` marks an exercise done one side at a time (all of a set on one
arm or leg, then the other): its target is per side, the plan view says so, and the session
estimate counts both sides. Alternating moves are not unilateral.

**Search (ADR 0007).** Derived, rebuildable indexes sit next to the catalog: the shipped
embedding file `catalog/search_index.sqlite` (built by `fitme catalog index`) and, in the app
DB, `catalog_search_fts` and `catalog_embeddings` (migration 0009, refreshed at startup).
`services/exercise_search.py` ranks an already-filtered allowed set for free-text search,
substitutes and `plan_generate`'s candidate pool; it never adds an exercise.

The catalog holds about 1,100 exercises covering every location in §5.1: the hand-written core plus reviewed entries imported from the local reference library (ADRs 0007, 0008). Pick
calibration start loads conservatively: an empty bar, the lightest dumbbell/machine stack, or
bodyweight. ADR 0011: `start` decides only bodyweight vs. calibration; its kg is never shown
as a starting weight.

### 4.5 Domain models (`src/fitme/domain/`)

Pure pydantic v2 models. The LLM output types, the DB JSON columns and the guards all use
them. ADR 0009 adds to the models below: a `Prescription` has one `measure` with exactly its
target (`reps_min`/`reps_max`, `seconds` or `meters`) and an optional `rir`; a `Workout`
has optional `qualities` (what the session is for); a superset is done in rounds in listed
order, each exercise's rest being the transition to the next and the last one's the rest
after the round. Bodies stored before ADR 0009 parse unchanged (reps, no qualities).
ADR 0011: a `Block` has an optional `role` (`warm_up`, `power`, `strength`, `accessory`,
`core`, `conditioning`, `mobility`), declared before its `items`, and a `Workout` declares
`qualities` (main objective first) before `title` and `blocks`, so a model states objectives
before choosing exercises. The last superset exercise's rest is the one round rest, shown
once. Bodies stored before parse unchanged (no roles; the review infers them).

**Activity items** (ADR 0018). `Prescription.exercise_id` is a catalog id, or an id in the
`activity:<slug>` namespace (`domain.models.ACTIVITY_PREFIX`, `is_activity_id`: slug of
3..60 characters `a-z0-9_`) for a non-catalog activity such as a class, a run or a walk.
An activity item needs `activity_name` (the display name, trimmed to 60 characters), is
measured in `time`, takes a `bodyweight` load and no `rir`; every other item must leave
`activity_name` empty. The guards skip the catalog, location, equipment, screening and
experience checks for it and record one `plan.activity` verdict; the plan-wide screening
gate still applies, and a bare unknown id still fails `plan.catalog_id`. It is rendered by
its name, with its note as the instructions, never by its id.

**Plan location.** `Plan.location` (optional, a profile `Location` value) is where that
plan is trained when it differs from the profile (an outdoor running plan for a gym
profile). The location-fit verdict uses it when set and the profile's location otherwise,
for the whole plan (`validate_plan`), for a workout trained from it on Start, review and
Save (`validate_workout(..., location=)`), and in the web editor and the recap. Equipment
is still the profile's.

**Set length.** `MAX_SET_SECONDS` is 10800 (3 h), so a 90-minute class fits as one timed
set. `set_logs.planned_seconds`/`actual_seconds` have only a lower-bound CHECK.

```python
class Load(BaseModel):
    kind: Literal["kg", "bodyweight", "calibration"]
    kg: float | None            # required when kind == "kg"; None otherwise

class Prescription(BaseModel):
    exercise_id: str            # must exist in catalog
    sets: conint(ge=1, le=10)
    reps_min: conint(ge=1, le=50)
    reps_max: conint(ge=1, le=50)
    load: Load
    rest_seconds: conint(ge=0, le=600)
    note: str | None = None     # short cue; no medical language

class Block(BaseModel):         # one exercise or a superset
    kind: Literal["single", "superset"]
    items: list[Prescription]   # len 1 for single, 2..4 for superset

class Workout(BaseModel):
    key: str                    # "A", "B", ...
    title: str
    blocks: list[Block]

class ScheduledDay(BaseModel):
    weekday: conint(ge=0, le=6)
    workout_key: str

class Plan(BaseModel):
    name: str
    schedule: list[ScheduledDay]
    workouts: list[Workout]

class Refusal(BaseModel):
    code: RefusalCode           # enum, e.g. NEEDS_CLEARANCE, OPEN_HEALTH_HOLD, NO_SAFE_EXERCISES, OUT_OF_SCOPE
    message: str                # plain language, user's language

PlanProposal = Plan | Refusal   # refusal is a first-class output (AGENTS.md §2)
```

### 4.6 Data access: controllers and selectors

No ORM. SQL is written by hand and kept in two places:

| Folder | Allowed statements | Returns |
|---|---|---|
| `db/controllers/` | `INSERT`, `UPDATE`, `DELETE` (create/update/delete) | `None`, or the new row id |
| `db/selectors/` | `SELECT` only | `domain` models or small frozen dataclasses. **Never** raw `Row` or tuples. |

The rules:

1. **SQL never leaves these files.** No SQL strings, `execute()` calls or row objects in
   `services/`, `bot/`, `web/`, `cli/` or anywhere else. A test enforces this: it scans
   `src/fitme` for `execute(`, `executemany(`, and SQL keywords at the start of string
   literals, and fails on any hit outside `db/`.
2. **One function = one operation**, with a descriptive name and typed arguments:
   `controllers.plans.insert_plan_version(conn, plan_id, version, body, origin, decision_id) -> int`,
   `selectors.training.historical_max_kg(conn, user_id, exercise_id) -> float | None`.
3. **Parameters only.** Use `?` or `:name` placeholders. Never format values into SQL with
   f-strings, `%` or `.format`. Dynamic identifiers (a table name in export/delete) come only
   from a hard-coded tuple in the same module.
4. **The first argument is always the connection.** Controllers and selectors never open
   connections or commit. Services own transactions:

   ```python
   async with db.transaction() as conn:          # BEGIN IMMEDIATE ... COMMIT / ROLLBACK
       plan_id = await controllers.plans.insert_plan(conn, ...)
       await controllers.plans.insert_plan_version(conn, plan_id, ...)
   ```

   Read-only paths use `async with db.read() as conn:`.

   One lock serializes all units of work on the shared connection (§3), and it is **not
   reentrant**. Services therefore:
   - never nest `transaction()`/`read()` (nesting deadlocks, and the connection raises on
     re-entry);
   - never await an LLM, Telegram or any other network call inside a unit of work. The
     pattern is: read → close → call the LLM → open a transaction → write.
5. **Append-only tables** (`plan_versions`, `decisions`, `decision_outcomes`) have insert
   functions only. The one exception is `controllers.account.delete_user`.
6. **JSON columns** are serialized and deserialized inside controllers and selectors, with
   the domain model's `model_dump_json()` / `model_validate_json()`. Callers never see JSON
   strings.
7. Selectors may join across tables for read models (stats, export). Controllers write to
   one aggregate per function.
8. **Tests:** every controller and selector function has a test against a real temporary
   SQLite file with all migrations applied. SQL is not mocked.

### 4.7 Migrations

- The files are `src/fitme/db/migrations/NNNN_short_name.sql`: plain SQLite SQL, numbered,
  forward-only. There are no down migrations: restore a backup instead.
- `db/migrate.py` does the following:
  - creates `schema_migrations(version INTEGER PRIMARY KEY, name TEXT, applied_at TEXT)`;
  - applies each missing file in order inside a transaction, with `executescript` wrapped
    in `BEGIN`/`COMMIT`;
  - records the file in `schema_migrations`;
  - refuses to run if an applied file's checksum changed (store `sha256` as a column).
- One SQL statement per line-group. Never put two statements on one line.
- Migration files must not contain their own `BEGIN`/`COMMIT`/`END`. The runner wraps
  each file in one transaction and rejects files that do.
- Foreign keys are switched off while a migration runs, and `PRAGMA foreign_key_check`
  must be clean before COMMIT. Table rebuilds would otherwise cascade-delete child rows.
- Never edit an applied migration. Write a new one. **The pre-release exception has ended** (2026-09-27): the operator runs a real database,
  created from `0001` as of commit 2e0905c. Every schema change is now a new numbered
  migration, and enum CHECK changes use the SQLite table-rebuild procedure. For SQLite table rebuilds (changing a
  column), follow the documented 12-step procedure inside the migration file.
- `fitme db upgrade` runs pending migrations. `fitme serve` refuses to start while any are
  pending.
- `0001_init.sql` creates every table in §4.1–4.3 with `STRICT` tables, `CHECK`
  constraints for enums, foreign keys with `ON DELETE CASCADE` from `users`, and indexes
  for the selector queries.

### 4.8 Reference data lives in files, not SQLite

SQLite holds what the instance records: the user, logs, plans, sessions and decisions.
Version-controlled files hold what the code relies on and ships with:

- the exercise catalog;
- stop-word lists;
- prompts;
- locales;
- the model price table.

The reasons:

- Changes to safety-relevant content (the catalog and stop words) are reviewed as diffs,
  covered by tests, and reverted with git.
- AGENTS.md §9 requires prompts in files.
- Every instance gets the same vetted content without a seeding step.

**Content version.** At startup, `config/content.py` computes a SHA-256 over the
**guard-relevant** content, in sorted path order: `catalog/exercises/**/*.toml`,
`guards/stop_words/*.txt`, `prompts/*.md`, **and the guard and catalog-logic source files**
(`guards/**/*.py`, `domain/catalog.py`, `domain/enums.py`, `domain/models.py`,
`services/loads.py`). Each file contributes
`path + length + bytes`, so moving content between files changes the hash. The first 12 hex characters are stored as
`content_version`. It is:

- written to every `decisions` row;
- logged once at startup;
- shown in `/system`.

This lets you reproduce what the guards saw for any past decision with
`git log -S <hash>`, or by recomputing the hash at a given commit. Locales and prices are
excluded because they don't affect guard outcomes.

## 5. Setup questionnaire (`/start` for a bound user without a profile)

Every step is an inline keyboard. Free text is used only where noted. Every step has
**Back** and a **/cancel** exit. Answers are saved step by step, so an interrupted setup
resumes. `/profile` shows the answers and lets the user change any of them. Changing a
screening answer re-runs the screening gate.

### 5.1 Steps

1. **Language.** Default comes from Telegram `from_user.language_code`, mapped to a
   supported locale (fallback `en`). Show it pre-selected with a **Change** option.
   Supported at launch: `en`, `ru`. Add more by adding a locale file.
2. **Timezone.** Needed to work out "today". Offer a short list of common IANA zones for the
   chosen language plus "type it" (validated with `zoneinfo`).
3. **Age range.** Buttons for the 7 buckets in §4.2.
4. **Weight range.** Buttons for the 17 buckets in §4.2, laid out 3 per row.
5. **Training experience.** Two questions:
   - "How long have you been training regularly, at least twice a week?" → `none`,
     `lt_6m`, `6m_2y`, `2y_5y`, `gt_5y`.
   - "Have you done barbell lifts (squat, deadlift, bench press) with confident technique?"
     → `yes`, `some`, `no`.
6. **Screening** (safety gate; AGENTS.md §2 "Screening before first plan"). This is a
   checklist of flags, modeled on PAR-Q-style readiness questions. It is **not** a
   diagnosis. The wording asks what might affect training.
   - **Red-flag conditions** (each yes/no): heart or cardiovascular condition; chest
     discomfort during activity; dizziness or fainting episodes; diagnosed high blood
     pressure; surgery in the last 6 months; currently pregnant; other condition a doctor
     said limits exercise.
     If any answer is **yes**, the bot asks "Has a doctor cleared you for strength
     training?". If the answer is not **yes**, plan generation returns
     `Refusal(NEEDS_CLEARANCE)` with a plain recommendation to talk to a doctor.
   - **Current injuries / sore areas** (multi-select): neck, shoulder, elbow/wrist, lower
     back, hip, knee, ankle, hernia, none. Each selection becomes a
     `<area>_injury_current` flag. It removes contraindicated exercises and turns on
     check-ins for that area.
   - **Other** → optional free text stored in `screening_notes`. It sets the flag
     `other_unlisted = yes`, which requires clearance like a red flag. The text is **never**
     put into a prompt.
7. **Training preferences** (multi-select): weight training, full body, split routine,
   bodyweight/calisthenics, conditioning, mobility.
8. **Focus** (single): strength, muscle, general fitness, conditioning. Do not offer
   weight-loss or body-composition targets (AGENTS.md §3).
9. **Location:** public gym, private/studio gym, home with equipment, apartment (no
   equipment), park/outdoor.
   - "Home with equipment" is followed by an equipment multi-select: dumbbells, barbell,
     rack, bench, pull-up bar, kettlebell, resistance bands.
10. **Frequency:** 1–6 sessions per week. **Session length:** 30 / 45 / 60 / 90 minutes.
11. **Summary + confirm.** The last screen shows everything, a **Fix** button per field,
    and the AI disclosure line.

## 6. Telegram bot

### 6.1 Access gate and activation

- `OwnerGateMiddleware` runs first on every update. If `from_user.id` is not the bound
  `telegram_accounts.telegram_user_id`:
  - `/activate <code>` is allowed only while **no** account is bound;
  - everything else gets one fixed, localized reply, and **nothing is stored**. Do not log

    The reply states facts only. There is no sign-up, waiting list or "contact the owner"
    call to action (ADR 0002).
- Activation flow:
  1. The operator runs `uv run fitme activate` on the server. It prints a one-time code

  2. The operator sends `/activate <code>` to the bot.
  3. The bot creates the `users` row (if none) and the `telegram_accounts` link, then starts
     setup.
  4. If an account is already bound, `/activate` is refused. Moving to a new Telegram
     account means `fitme activate --rebind`, which unlinks the old account first.

### 6.3 Bot conventions

- Every message is built in the user's language through `i18n`. No hard-coded strings in
  handlers.
- Callback data is short and structured, e.g. `tr:done:<session_id>:<block>`. Validate it
  and check that it belongs to the current session and state. Ignore stale callbacks and
  answer them with a short toast.
- Every free-text message is saved to `chat_messages` (the retention job purges it) and
  **passes the stop-word guard before anything else, including the LLM** (§7.4).
- Keep a persistent **⚠ Pain / feeling unwell** button on every in-workout message. It
  always triggers the halt path (§6.6).
- Free text that no command, pending prompt or setup step claims goes to the **free-text
  assistant** (ADR 0003, ADR 0004), after the stop-word scan and the `/plan` gate. It works
  in **sessions** that remember their last 100 messages in both directions
  (`services.conversations.HISTORY_LIMIT`; 20 before 2026-10-17):
  - **Planning**: a new plan, or changes to one plan, iterated on a draft. Each step is
    judged like any draft and shown as a diff, with **Save** / **Whole draft** / **Close
    without saving**. Loads above the guards are limited and the user is told. The website
    editor's checkbox is still the only override.
  - **Training**: from Start to the end of the workout. Each exercise of the current block
    (one at a time in a superset) can be logged as planned ("по плану"), with the user's
    numbers, or skipped. It is written at once, with no confirmation step, but only after
    the coverage and plausibility checks pass (ADR 0005). This is the only way to log
    results that differ from the plan (ADR 0013). A safety concern that the stop words
    missed halts the workout. Changes to the blocks not started yet apply for today
    only. At the end the bot offers to carry those changes into the plan, as a
    planning draft. Aborting stays a button only.
  - The assistant uses tools and may call several in one turn. Staging tools check each
    action at once and apply it only after the run, through the guards. Logged-set
    corrections of finished sessions apply with **Undo**.

### 6.4 `/plan` — generate and iterate

```
check gates ──► build context ──► LLM: propose ──► guards ──► show ──► user: confirm | revise(text)
    │                                                 │                        │
    └─ open health hold / missing clearance           └─ violation: retry once └─ loop back to LLM
       ⇒ Refusal, stop                                   with feedback, else Refusal
```

**ADR 0009.** The model gets `requested_qualities` (read from the request, the other sport,
focus and preferences) and a pool that includes exercises directly training each of them;
a plan that passes the guards is reviewed by `services/plan_quality` (session goals vs
exercises, warm-up and order, supersets, weekly shoulder/leg load), and findings spend the
feedback retry as a targeted repair — the passing attempt with the fewest findings becomes
the draft, remaining findings are logged, never a refusal. Hard exclusions
(`exercise_exclusions`) are removed from the allowed set and rejected by `plan.excluded`;
ADR 0010: only those that apply to the plan being worked on (scope `all`, that plan's
`plan`, or the new draft's `new_plan`).

**ADR 0011.** Before any exercise is chosen, `services/programming` builds a deterministic
`programming_brief` (sessions and length, a working-block budget, main and secondary
qualities, full-body-with-different-emphases vs split, the other sport's fatigue budget, the
session order). The pool adds general warm-up activities and ranks narrow drills last;
`exercise_facts` carry each exercise's `intensity`. `services/prescribing` drops an `rir` on
power, speed, carry or interval work and words every unknown load by its stimulus, never
with the catalog `start` weight. The review adds block roles and order, direct vs supporting
coverage (warm-ups don't count), power-set prescriptions, splits nobody asked for and session
length.

**ADR 0016.** Session length is estimated in code (`services/session_time`: reps, seconds or
meters per set, both sides of a `unilateral` exercise, rests between sets, superset rounds,
setup by equipment; a planning estimate only, 15% uncertainty). A generated workout over the
user's session length is shortened toward it by objective relevance (`services/time_budget`:
redundant accessories, then one set at a time off the lowest-priority blocks, then those
blocks; never the warm-up, the main objective's work or a rest), logged as
`plan.time_budget`, and validated again before the review; revisions, imports and edits are
only reviewed. A valid workout still over the length is accepted, and the plan view (bot and
web) shows "⚠ Requested … Estimated …" under its estimate (`time_budget.duration_warning`). The
weekly review weighs sets by stimulus (`services/workload`: load units per region, a heavy
set 1, a drill 0.25, a stretch 0) and adds `hinge_overlap` and `off_objective`. The brief
adds `session_objectives` (main objectives spread over the sessions) and `time_budget`; the
plan view shows each workout's estimate, labelled as one.

1. **Gates** (guards, before any LLM call): the profile is complete; there is no open
   `health_hold`; red-flag clearance is present. Any failure returns a `Refusal`, which is
   logged as a `decision(kind=refusal)`. The bot shows a refusal by its per-code copy, except
   `out_of_scope`, where the model's own short explanation is shown if it passes the wording
   check (`bot.rendering.refusal_text`); safety codes always keep the fixed copy.
   **Guidance.** If the gates pass and the user already has plans, **New plan** first asks
   what the new one should be ("a gym version of my home plan", "more upper body"), with
   **Generate anyway** and **Cancel**. The answer is free text: stop-word scan first (§6.3),
   then it goes to the assistant in the new plan's planning session, which may ask one
   clarifying question before it calls `new_plan` (ADR 0017); its guidance reaches
   `plan_generate` as `user_request`. A compact `existing_plans` summary goes
   with it (scrubbed names, workout titles, exercise ids, no loads) whenever plans exist, so
   the request can refer to them and the new plan isn't a copy. The website's new-plan form
   has the same optional field. Prompt: `plan_generate.v2.md`.
2. **Context** (`llm/context.py`) is pseudonymized: `user <id>`, buckets, experience,
   location, equipment, preferences, focus, frequency, session length, **flag codes**, the
   **allowed exercise ids** (catalog filtered by location, equipment and contraindications),
   and a history summary (per exercise: last working load, reps, historical max).
   **Request frame** (ADR 0017, `services.plan_request`): the request's activity, sessions,
   weekdays, length and an outdoor setting replace the profile's defaults; when it names an
   activity or a quality, focus and preferences are left out and history is limited to
   exercises that serve it (physical data only).
3. **LLM** (`plan_generate` agent, output type `PlanProposal`).
4. **Guards** (`guards.validate_plan`, §7). On a violation, re-prompt once with the list of
   violations. If the second attempt also fails, return a `Refusal(NO_SAFE_PLAN)`. Every
   attempt is logged.
5. **Show** the plan as structured text: schedule, then each workout with exercises, sets ×
   reps, and explicit load (`kg`, `bodyweight`, or a calibration that says how to choose the
   load for the exercise's stimulus, ADR 0011). Buttons: **Confirm**, **Change something**, **Cancel**.
6. **Revise**: free text ("no lunges, 3 days not 4") goes to the `plan_revise` agent with the
   current draft. The result goes through steps 4–5 again. Each round is a decision.
7. **Confirm** stores `plans` + `plan_versions(version=1, origin=llm)`. If this is the only
   plan, it becomes the default.

#### 6.4.1 The conversational planner

ADR 0018 (accepted 2026-10-18) records this path; the experiment report is
`docs/reports/llm-first-planning-experiment.md`.

On this branch, steps 1–6 above are reached only through **Generate anyway**; the default
path is the `planner` agent (§8.1, `prompts/planner.v2.md`).

- **Entry.** Every free-text message outside a started workout (`services.assistant.
  handle_message`: no active `/train` session) runs `planner`; a started workout keeps the
  legacy `assistant` and its logging tools. **New plan** always asks what the plan should
  be first (also with no plans yet), **Change** on a draft and **Change something** on a
  saved plan answer "what should change?" in that plan's planning session — none of them
  sets a pending revision, so the next text reaches the planner with the draft in
  `state.planning_session.draft` and the session's turns in `history` (Change on a draft
  whose session idled out makes it the session's draft again). An exchange that starts
  outside any session opens a new plan's planning session, so the next message sees it
  (not after a turn that saved or closed one). A planner draft for another plan than a
  draftless session's moves that session to it (`conversations.open_planning(retarget=)`):
  its messages stay, and exclusions made for the new plan move to that plan — the staged
  plan is already judged (staged, recorded and saved) with them. An exclusion the user
  stated about that plan stays on it even if the draft is then cancelled. `/cancel` closes
  an open planning session.
- **Tools.** Lookups (`list_plans`, `get_plan`, `list_recent_sessions`, `get_session`,
  `find_exercises`, `find_substitutes`), `stage_plan(plan, plan_id)`, `save_draft`,
  `discard_draft`, `rename_plan`, `set_default_plan`, the exclusions, `fix_logged_sets`,
  `report_safety_concern`, `show`. No typed edit ops, no `rewrite_plan`/`new_plan`, no
  workout logging.
- **What runs.** The model talks the plan through in plain language and, when the user
  agrees, stages a whole `Plan` (catalog ids, `activity:` items, an optional `location`).
  `stage_plan(plan, plan_id)`: `plan_id` is the saved plan it changes, null a new plan; a
  current draft of another plan in the session must be saved or closed first. It replaces
  any `declared_kg` with the base's and judges the plan with `planning.judge` (no scope)
  against inputs read for the target plan (its own exclusions): hard guards with
  load-engine substitution, wording, measure and intensity repair. A failure goes back to
  the model in the same run; nothing is staged. A success answers only the load notes and
  what was repaired. The planner's `find_exercises`/`find_substitutes` rank what the user
  may do at any location (the plan's location is what the guards judge) and give each
  hit's `kg_loadable`, `load_unit`, `equipment` and `locations`; `find_exercises(queries)`
  takes every name at once (one model request, one embedding request). A run is capped at
  `PLANNER_REQUEST_LIMIT` (30) model requests (the assistant: 15); hitting the cap is the
  `LLM_UNAVAILABLE` refusal, logged with cause `request_limit`. The programming brief, candidate pool,
  `plan_quality.review`, `time_budget` and `plan_generate`/`plan_revise` do **not** run.
- **Draft, show, save.** After the run the staged plan becomes a `plan_revise` draft round
  (`planning.record_edit_draft`, `user_report.base = "planner_stage"`, the planner's prompt
  version and model) and the session's draft. The bot shows it whole with Confirm / Change /
  Cancel, titled with the plan it changes when it has one (no session-length warning: the
  profile's length is a default), then any load the guards limited. A "save it" whose draft
  fails when recorded saves nothing. Confirm — or `save_draft` in the same turn when the user said "save it" —
  is the unchanged `planning.confirm_plan` (a new `plans` row for a new plan,
  `plan_versions.origin = llm`).

### 6.5 `/train` — the workout loop

The state machine is stored in `workout_sessions.status` and `current_block`:

```
select_plan ─► select_workout ─► precheck ─► review ─► in_progress ─► recap ─► completed
                                     │           ▲ │        │
                                     │     adjust└─┘        ├─► halted (stop word / pain button / LLM safety signal)
                                     └─► halted             └─► aborted (user)
```

1. **Select plan.** Use the default plan, or the only one. Otherwise list the plans as
   buttons.
2. **Select workout.** Use the workout scheduled for today in the user's timezone. If there
   is none, use the next one in rotation after the last completed one. Offer **Pick
   another**. If a session is `in_progress`, offer **Resume** first.
3. **Precheck.** "Since your last session, have you had pain (not normal muscle soreness),
   dizziness, numbness, chest discomfort, or felt something pop?" → **No** / **Yes**.
   **Yes** → halt (§6.6). Anything other than **No** means the session does not start.
4. **Review.** Send the whole workout with explicit loads. The loads come from the
   **load engine** (§7.3), not stored plan numbers alone. Buttons: **Start**, **Adjust**.
   **Adjust** takes free text → `session_adjust` agent → guards → re-show. This repeats
   until **Start**. Adjustments apply to this session only, unless the user also picks
   **Save to plan**, which creates a new plan version.
5. **In progress.** Send one block at a time (a single exercise or a superset):
   - exercise name, vetted catalog instructions, sets × reps, **explicit load for every
     set** ("3 × 8 @ 42.5 kg"), rest time;
   - buttons: **✅ Done as planned**, **⏭ Skip**, **⚠ Pain / feeling unwell**.
   - **Done as planned** writes `set_logs` with actual = planned.
   - Anything else is written as a message ("8,8,6 at 42.5, last set hard"): stop-word
     guard → the free-text assistant (§6.3), which logs each exercise through
     `services.training.log_items` after the coverage and plausibility checks, or halts on
     a safety concern (ADR 0005, ADR 0013). There is no separate ✏️ result-entry button.
6. **Recap** (end of workout):
   - Deterministic summary: completed vs planned, volume, any new historical max.
   - **Check-ins**: one question per flagged area loaded today ("How did your lower back
     feel?" → Fine / Worse than usual / Pain). An unanswered check-in stays `unknown`.
     **Pain** → health hold + doctor recommendation.
   - **Progression**: the load engine computes the next loads (§7.3). The `recap` agent only
     writes a short explanation of those numbers and may suggest non-load changes (swap an
     exercise, change the rep range). Suggested plan changes need the user's **Apply** →
     guards → new `plan_version(origin=progression)`.
   - Decision logged with the planned vs actual numbers, check-ins and guards fired.

### 6.5.1 Workout loop details (settled in M7)

- **Starting the workout.** The decision written at Start is `kind=session_adjust`,
  `event=start`, even when nothing was adjusted. It carries the exact workout trained and
  the `load_changes` applied by starting it: engine or adjusted increases, counted once.
- **Supersets.** Results are logged one exercise at a time, so `set_index` is unambiguous.
- **`/cancel` during `in_progress`.** The workout is kept and can be resumed; an explicit
  **Abort workout** button aborts it. `/cancel` on an unstarted session aborts it.
- **Plausibility guard (`guards/plausibility.py`).** A load the assistant reports is
  refused (the assistant asks the user to check it), never stored, when any of these holds:
  - it is not finite, or it is ≤ 0;
  - it is kg on an exercise where `kg_loadable = false`;
  - it is more than 2× the prescription;
  - it is more than the prescription + 3 increments;
  - it is exactly 2× the prescription on a `per_implement` exercise.
  - For calibration or bodyweight prescriptions, the ratio rules use the known
    historical max as the reference, when there is one.
  - **Absolute bounds** apply always, including in calibration: > 300 kg for a `total` load,
    or > 60 kg for a `per_implement`/`single_implement` load.
  - The `assistant` prompt treats a comma between digits followed by one or two digits
    ("42,5") as a decimal separator, and asks when the numbers are ambiguous.
- **Adjust drafts.** Only guard-accepted adjust attempts can become the current draft
  (`event=adjust`). Rejected attempts and refusals are logged as `event=adjust_rejected`,
  and the last accepted draft stays in effect.
- **"✅ Done as planned"** logs every set at the top of the rep range. The hint under every
  block says so; otherwise the user writes the results as a message (ADR 0005, ADR 0013).
  On a block where every load is calibration ✅ is hidden, and the weight used is written
  as a message.
- **Start and Save judge today's workout**, not the whole plan: the gate plus
  per-prescription verdicts. They use train-specific refusal copy.

### 6.6 Halt path (stop words, pain button, LLM safety signal, precheck yes)

1. Set the session status to `halted` with `halt_reason`.
2. Create a `health_hold`.
3. Log `decision(kind=session_halt)`.
4. Send a fixed, **non-LLM**, localized message: stop training for today; if you have pain,
   dizziness, numbness, chest discomfort, or something popped, contact a doctor (for chest
   pain or severe symptoms, call emergency services).
   - Offer **no** alternative exercises and **no** lighter option (AGENTS.md §2).

While a hold is open, `/plan` and `/train` refuse. To clear the hold the next day (in the
user's timezone) or later, the user has to answer a direct question with a button: "Are you
now free of pain, dizziness, numbness and chest discomfort?" → **Yes, clear**. Clearing is
logged as a `hold_clear` decision. Holds cannot be cleared on the same day. "Same day"
is evaluated in the timezone in effect **when the hold was created**, which is recorded in
the halt decision's `user_report`. At least 12 hours must also have passed, so changing the
timezone can't shorten a hold. The only bypass is on the operator's server shell: `fitme hold clear --yes` asks for a typed confirmation and writes a `hold_clear` decision with `source=operator_cli`. It exists for false positives. The bot has no bypass.

### 6.7 `/stats` (short)

- Last 4 weeks: sessions completed vs scheduled (scheduled = the default plan's days per
  week, else the profile's; neutral wording, **no streaks**, no shaming), total volume, top 3 lifts with current working load and change.
- Next scheduled workouts (3).
- A link to the website for charts.

Do not send reminders or notifications about missed days (AGENTS.md §4). An optional
neutral reminder for a scheduled day ("Workout B is scheduled today") is off by default and
out of scope for v1.

## 7. Guards (`src/fitme/guards/`)

Guards are pure functions over domain objects with no I/O. They return verdicts. They do not
raise for business outcomes. Services fetch the inputs from the DB and pass them in.

```python
class GuardVerdict(BaseModel):
    rule: str          # e.g. "progression.weekly_cap"
    ok: bool
    detail: str        # machine-readable-ish reason, logged to decisions.guards_fired
```

| Module | Function | Rule (AGENTS.md §2) |
|---|---|---|
| `progression.py` | `check_weekly_increment(exercise, *, increases_7d, proposed_increase_kg, cap_kg) -> GuardVerdict` | The sum of **positive** increases over a trailing 7 days, plus the proposed increase, must be ≤ the per-exercise cap (default 2.5 kg for compounds, catalog may set lower). Proposals above it are **rejected**, not clamped. `increases_7d` is the positive `to_kg − from_kg` of every `load_changes` entry for that exercise in `decisions` of **any** kind (progression, revise, adjust, user_edit). It is read from the append-only log, **not** from `set_logs`, so deleting a training log cannot reset the cap (§9.4). |
| `ceiling.py` | `check_ceiling(*, history_max_kg, proposed_load_kg, increment_kg) -> GuardVerdict` | proposed ≤ historical max + one increment. With no history, only a `calibration` load (the catalog start) is allowed. |
| `checkins.py` | `increase_allowed(exercise, checkins, flagged_areas) -> GuardVerdict` | Check-ins are asked for **flagged** areas only (§6.5). For every area the exercise loads **that the user flagged**, the latest check-in must be `fine`. A missing, `unknown`, `worse` or `pain` answer blocks the increase (silence is not consent). Areas the user did not flag need no check-in. An exercise with empty `loads_areas` fails closed. Because the catalog contraindicates every exercise that loads a flagged area, this gate only matters for exercises with a reviewed `contraindication_exceptions` entry. It is kept as defense in depth. |
| `stop_words.py` | `scan(text, lang) -> StopHit \| None` | Normalizes the text (casefold, strip punctuation) and matches the per-language lists in `stop_words/*.txt` (pain, dizzy, numb, chest, popped, ... and inflections). **Any match halts.** Runs before the LLM. |
| `screening.py` | `plan_allowed(flags, holds) -> GuardVerdict`; `exercise_allowed(exercise, flags) -> GuardVerdict` | Every red flag must have an explicit `yes`/`no` answer. Missing or `unknown` → `Refusal(SCREENING_INCOMPLETE)` (silence is not consent). Red flags answered `yes` need clearance. Open holds refuse. Contraindications remove exercises. |
| `plan.py` | `validate_plan(plan, ctx) -> list[GuardVerdict]` | ADR 0009: `plan.excluded` rejects an exercise the user's hard exclusions remove (plan-level only; `validate_workout` doesn't run it, so a saved plan still trains). Runs all the checks above (including `plan_allowed`) over every prescription, plus: catalog ids only, location and equipment fit, at least one scheduled day (the profile's frequency is the default a plan is generated with, not a rule: a plan may have fewer or more days), reps_min ≤ reps_max, superset size. **Reference load:** an increase is measured against the exercise's **current working load**, not the historical max. When both are known, the reference is `min(current, history_max)`. **An increase already applied in the trailing 7 days is not counted twice.** If a `to_kg` from an applied `load_changes` entry for the exercise, is above that reference, the reference becomes the highest such applied `to_kg`. An applied change is discarded only when the exercise's last completed session **after** the change was **prescribed below** its `to_kg`, i.e. the user has since trained at a lower prescription. A load the user just failed at therefore cannot be restored through the lift. A skipped or lighter-logged session at the applied prescription keeps the lift, so keeping that load is a hold, not a new increase. Two kinds of applied change never lift the reference (they still count toward the weekly cap):
  - **over-cap `user_edit` changes**, i.e. edits the user confirmed past the caps;
  - **changes made before a `session_delete` that removed a completed session.** Deleting logs must never raise what the system allows (§9.4). The engine's decrease rule also has priority over holding at an applied load. Keeping a confirmed load is therefore not a new increase, and only the part above it counts toward the cap. The earlier change was guarded when it was applied, and `check_ceiling` still runs as the absolute backstop. The current working load is the prescribed load of the last completed session (the logged load, when that session was a calibration: the engine holds there, §7.3), falling back to the active plan version's prescription. If there is history but no current load, the historical max is the reference, and the increase checks still run. Any `proposed > current` must pass `check_weekly_increment` and `increase_allowed`. `check_ceiling` always runs as an absolute backstop. |

All load inputs must be finite and positive. Guards **fail closed** on NaN, infinity or non-positive values.

### 7.1 Stop-word false positives

Matching is deliberately broad. "No pain today" halts too.

- **Chest and heart need a symptom** (operator decision, 2026-09-27). Chest is extremely
  common in training text ("к верху груди", "на уровне груди", "грудью на скамье", "chest
  day"), so a bare mention never halts. A chest or heart token (`chest`, `heart*`, `sternum`,
  `груд*` incl. `грудин*`, `сердц*`) halts only when a **symptom descriptor** appears in the
  same clause (the same sentence fragment, within a few words):
  - EN descriptors: tight*, pressure, pain*, hurt*, squeez*, ache/aching, discomfort,
    pounding, racing, flutter*, burning, heavy/heaviness;
  - RU descriptors: давит/давлен*, сжим*/сдавл*, колет/кольн*, ноет, щем*, стеснен*,
    жж*/жжение, тяжест*/тяжело, the pain forms of боль, дискомфорт, колотит*, перебои.

  Explicit cardiac terms halt on their own: palpitations, arrhythmia/аритмия, "irregular
  heartbeat", "heart racing/pounding", "за грудиной".
  Exercise wording ("жим груди", "chest press 3x8", "heart rate 150") never halts, even
  next to effort words.
- **Something popped:** bare `popped`, plus "went pop", "heard/felt it pop", "felt a pop",
  RU `щелк*`/`щелч*`/`хруст*`/`лопн*`. False positives like "popped a PR" are accepted.
- **Prefer phrases over stems when a stem collides with plan-editing language.** For
  example: "tweaked my" (not `tweak*`, because of "tweak the plan"); "heard a crack" (not
  `crack*`, because of "cracked the plateau"). Free text in revise/adjust also passes
  this guard.
- **Weakness:** only limb-specific phrases halt ("arm went weak", "слабость в руке/ноге").
  Bare "weak" or "tired" does not. Cramps do not halt.
- **Russian uses a curated stem list.** Each stem (`онеме`, `головокруж`, `обморок`,
  `покалыва`, `прихват`, `растян`, `надорв`, …) has a negative test against common
  innocent words.
- **Breathing:** inability to breathe halts, in present and past tense and with or
  without an apostrophe ("can't/cant/couldn't/could not breathe", "hard/struggling to
  breathe", "trouble breathing", "не могу дышать", "задыхаюсь", "не хватает воздуха",
  "нечем дышать"). Ordinary exertional breathlessness does not halt ("out of breath",
  "can't catch my breath", "одышка" after conditioning).
- **Nausea:** only unambiguous terms halt ("threw up", "vomited", "nauseous", "рвота",
  "тошнит", "тошнота", "мутит", "вырвало", "стошнило"). Vague phrases like "felt sick" do not.
- **Everyday logging must not halt.** Examples: heart-rate logging ("heart rate 150",
  "zone 2"), chest-day slang ("день груди", "грудь и трицепс", "грудные мышцы"), and set
  results.
- **Normalization before matching:**
  - strip Unicode `Cf` characters (soft hyphen, zero-width space) **before** punctuation;
  - fold apostrophe variants ("can't", "cant", "can t", "cannot" → one form);
  - map a small emoji table to categories (🤕 😵‍💫 🫀 💔 …);
  - for a Russian-interface user, transliterate Latin-script Russian ("bolit", "golova
    kruzhitsya") to Cyrillic and scan both forms. It is not applied for an English
    interface, where Latin text is English. Cyrillic text is scanned under every interface
    language.
- **Residual risk:** mixed-script homoglyphs ("бoлит" with a Latin o) under an English
  interface are not caught.
- **Residual risk:** typos ("pian", "dizy") are not caught. Buttons (precheck, check-ins,
  the ⚠ button) are the primary path; free text is the secondary one.
- A parametrized regression corpus of realistic reports in each language lives in
  `tests/guards/`. Every phrase added to it must halt, and every innocent phrase in it must
  not. That is the accepted cost: the
guard must be deterministic, and it must not be possible to argue around it. The halt
message says that if this was a misunderstanding, the user can clear the hold tomorrow.
Precheck and check-ins use buttons, not free text, so false positives stay rare.

### 7.2 Guard layering

LLM safety signals (`safety_signal` fields, refusals) can **add** halts or refusals. They
can never remove one that a deterministic guard produced.

### 7.3 Load engine (`services/loads.py`, uses guards)

The engine produces the explicit loads shown in review and recap. It is deterministic
double progression:

- **No history** for an exercise → `Load(kind="calibration")`. The engine never emits a kg
  value without history. The catalog `start` is only a display hint ("calibration: start
  with 20 kg or lighter, log what you used"). The user logs what
  they actually used. There is no progression until one session is completed (AGENTS.md:
  the first session is data collection).
- Only `completed` sessions count. A session with any prescribed set `skipped`, unlogged,
  or performed below the prescribed load is **not** a success.
- Progression is computed from the **prescribed** load of the last successful session, not
  from what the user logged. Logging a heavier weight than prescribed does not jump the
  next prescription. It only raises the historical max used by the ceiling.
- **All prescribed sets hit reps_max** at the prescribed load, **and** `increase_allowed`
  passes →
  propose + `increment_kg`, then check `check_weekly_increment` and `check_ceiling`. If
  either fails, keep the load.
- **Did more than prescribed** (ADR 0014): every prescribed set performed at or above the
  prescribed kg load with at least reps_min, plus an extra set at that standard (ADR 0012)
  or a heavier load on every prescribed set → the same single increment from the
  **prescribed** load, under the same guards. Only the prescribed sets decide success and
  failure otherwise: an extra set never makes or breaks `hit_reps_max`.
- **Any set below reps_min** → hold. Two sessions in a row below reps_min → propose −10%,
  floored to the implement step, and always at least one step down. If that would reach
  ≤ 0, fall back to a `calibration` load (log what you used). Never fall back to the
  catalog's kg start, and a decrease can never return a load above the current one. Decreases are always allowed.
- **After a calibration session**, the next session is prescribed at the load the user
  logged (a hold, not an increase). If nothing usable was logged, it is calibration again.
  It never uses the catalog kg start. Progression starts from the first prescribed
  session.
- **Every kg value the engine emits, on every path (increase, hold, decrease), must pass
  `check_ceiling`.** A hold above the ceiling is clamped down to the ceiling, floored to
  the step (decreases are always allowed), or falls back to calibration.
- **Pasted plans (M8b).** A kg load on an exercise with no history becomes `calibration`.
  The user's number is kept as `Prescription.declared_kg`, which is display-only, bounded
  and untrusted. The guards and the engine never read it.
- **Recency is chronological.** "Last completed session" means the latest `finished_at`
  (ties broken by id), not insert order, so older imported history never counts as the
  most recent session.
- **Imported history (M11).** Imported sessions are completed sessions whose prescribed
  load equals the logged load. They **never count as a success** for progression, so the
  first app session after an import holds at the imported load. They set the history max
  and the current load, write no
  `load_changes`, never trigger a recap, and belong to no plan
  (`plan_version_id` NULL). There is no holder plan; migration 0007 removes any created by
  earlier imports. An imported `[[plan]]` is judged the same way as a pasted plan (M8b,
  `judge_import`, above) against a `GuardContext` built after the file's sessions are
  written: a structural failure rejects that plan, but a load-only violation is substituted
  with the engine's value and saved, the declared number kept as the `declared_kg` hint. See
  `docs/import-format.md`.
- **Speed work** (ADR 0016): an exercise whose first quality is power, rotational power or
  agility (`IntensityMode.SPEED`) holds its load (`LoadKind.HOLD_SPEED`, under the ceiling
  like every hold): topping its reps never raises it, short sets never lower it, and
  calibration still comes first. It progresses by speed and technique, which the app
  doesn't measure and never claims.
- **Plan and prescription scope** (ADR 0016, `scope_history`): where a prescription's load
  is decided for a plan (review, Start, recap preview), only sessions of the same sets and
  rep range in the same plan are successes or failures; others only inform the load, and a
  higher rep target than the last load was used for is calibration.
- **Work the engine doesn't progress** (ADR 0016, `services/progression`): bodyweight reps,
  and any timed or distance prescription. Two completed app sessions of the same plan in a
  row at the current sets and target (and, for a loaded carry, the same logged resistance)
  with every prescribed set at its top → one step up (rep range +1–2, or about 10%
  more seconds or meters); two in a row short of it → one step down; otherwise hold; speed
  work keeps its volume; at the top of a useful range a harder variation is next. The recap
  offers the change as a `change_reps`/`change_target` suggestion, applied only on **Apply**
  as an `origin=progression` plan version.
- Every decision that applies a load records it in `decisions.load_changes`.
- Otherwise → hold.

When an LLM proposes a load (revise, adjust), the same guards judge it. A violating proposal
is rejected, and the engine's value is used, with the reason logged.

### 7.4 Tests (`tests/guards/`)

At least one test per rule proves that it **blocks** the bad case (AGENTS.md §9):

- the weekly cap is exceeded;
- the ceiling is exceeded;
- there is no history but a kg load is proposed;
- an unknown check-in blocks an increase;
- each stop-word category in each language;
- a red flag without clearance leads to refusal;
- an open hold leads to refusal;
- a contraindicated exercise is rejected;
- a non-catalog exercise is rejected;
- LLM `safety_signal=false` does not clear a stop-word hit.

## 8. LLM layer (`src/fitme/llm/`)

### 8.1 Agents

One pydantic-ai `Agent` per purpose. Each has a typed output, and its prompt is loaded from
`src/fitme/prompts/<name>.v<N>.md`.

| Agent | Input | Output type | Default tier |
|---|---|---|---|
| `plan_generate` | pseudonymized context | `PlanProposal` | large |
| `plan_revise` | context + current plan + user request | `PlanProposal` | medium |
| `session_adjust` | context + today's workout + user request | `Workout \| Refusal` | medium |
| `plan_import` | context + `imported_text` (scrubbed) | `PlanImport{plan, unmatched} \| Refusal` | medium |
| `recap` | planned vs actual (incl. `extra_sets`) + engine decisions + `next_targets` (ADR 0016) | `Recap { text: str, suggestions: list[PlanChange] }` (swap, rep range, set count — ADR 0015; timed/distance target — ADR 0016) | large |
| `assistant` | context + `state` + session `history` + user text (scrubbed); lookup and staging tools | `AssistantTurn \| Refusal` (ADR 0003, ADR 0004) | medium |
| `planner` | as `assistant`; lookups, `stage_plan` (a whole `Plan`) and session tools, no typed edits or logging (§6.4.1) | `AssistantTurn \| Refusal` | large |

- The prompt loader returns `(template_name, version, rendered_text)`. Template name and
  version go into `decisions`. Current versions (ADR 0017): `plan_generate.v8`,
  `plan_revise.v5`, `plan_import.v2`, `session_adjust.v2`, `recap.v3`,
  `assistant.v12`, `planner.v2`. (`result_parse` was removed with the ✏️ button, ADR 0013.)
- Each agent's model comes from its tier or override (§8.5). Nothing in the code is tied to
  one provider.
- `llm/usage.py` wraps every run: records `llm_calls` from `result.usage` (a property), latency, and
  the cost estimate from the price table.
- Every prompt says, in the user's language: training plan generator, not a
  coach/doctor/physio; no medical claims; no weight-loss claims; use catalog exercises only;
  return a Refusal when unsure.

### 8.2 Pseudonymization (`llm/context.py`)

- Allowed in prompts: internal `user_id`, bucket enums, flag **codes**, catalog ids,
  numbers from `set_logs`, and the user's in-flow free text (plan requests, result text).
- Before free text is sent, `scrub()` removes @handles, emails, phone numbers and URLs.
- **Never** sent: `telegram_user_id`, `chat_id`, names, `screening_notes`.
- **Scrub scope:** the scrub removes handles, links, phone numbers and emails, including
  the Russian domestic phone format, scheme-less domains with a known TLD, `[at]` emails
  and `.рф` domains. It must not damage result text: rep lists, load ramps ("140 150
  160"), "3x10.Next" and dates survive.
- **Accepted residual risk:** some identifiers can't be caught without heavy false
  positives on training text:
  - bare handles without `@` ("my tg is ivan_petrov");
  - deliberately spaced obfuscation ("t . me / ivan", "ivan at mail dot ru");
  - personal names typed in free text.
- **Per-agent minimization:** each agent receives only the context fields it needs. For
  example, `recap` gets the planned-vs-actual numbers and the engine's decisions, not the
  allowed-ids list or the history.
- A unit test builds a context from a fixture and asserts that none of the forbidden values
  appear in the rendered prompt.

### 8.3 Export & delete

- `services/account.py::export_user(user_id) -> dict`: every row in every table for that
  user, as JSON, grouped by table. Used by `/export` and `fitme export --out file.json`.
- `services/account.py::delete_user(user_id)`: deletes all rows in one transaction,
  children first, then runs `VACUUM`. This includes `decisions` (deleting the account
  overrides log immutability). Used by `/delete` and `fitme delete --yes`.
- An integration test seeds every table, deletes the user, and asserts that no table holds a
  row for them.

### 8.4 Retention job

Runs daily. It deletes:

- `chat_messages` older than `FITME_CHAT_RETENTION_DAYS`, and `conversations` closed before
  that cutoff;
- expired `login_codes`, `activation_codes` and `web_sessions`.

It keeps the structured training log.

### 8.5 Model tiers

Different jobs need different model sizes. Building a plan from scratch benefits from the
largest model. Parsing "8,8,6 at 42.5" does not.

| Tier | Default model | Used for | Why |
|---|---|---|---|
| `large` | `anthropic:claude-opus-5` | `plan_generate`, `recap` | Whole-program design: exercise selection under constraints, balance, schedule. Rare (a few calls per month), so cost barely matters. The recap (ADR 0015) reads each finished workout for the next plan changes; once per workout. |
| `medium` | `anthropic:claude-sonnet-5` | `plan_revise`, `session_adjust` | Targeted edits to an existing structure. Frequent, interactive, latency-sensitive. |
| `small` | `anthropic:claude-haiku-4-5` | none by default (ADR 0013, 0015) | Kept for `FITME_LLM_AGENT_<NAME>` overrides. |

Rules:

1. **Resolution** (`llm/models.py::model_for(agent) -> ModelSpec`):
   - `FITME_LLM_AGENT_<NAME>` wins if it is set;
   - otherwise the agent's default tier from the table in §8.1, resolved through
     `FITME_LLM_TIER_*`.

   The mapping from agent to default tier lives in code, as a plain dict in `llm/models.py`.
   Env vars only override it. Config is validated at startup: an unknown tier name or a
   model string pydantic-ai can't parse fails fast.
2. **Guards don't care about tiers.** A cheaper model is safe to use because every output
   goes through the same deterministic guards (§7). A cheaper model can only produce more
   rejections, never a less safe plan.
3. **Escalate once, then refuse.** For `plan_revise` and `session_adjust`, if both attempts
   (the first and the guard-feedback retry) fail the guards, make **one** more attempt on
   the `large` tier before returning a `Refusal`. Log every attempt as its own `llm_calls`
   row, with the model used.
4. **Provider errors are refusals, not fallbacks to guesses.** Timeouts, rate limits and
   provider-side refusals become `Refusal(code=LLM_UNAVAILABLE)` after pydantic-ai's normal
   retries. Never fall back to the previous plan with changed numbers, and never fall back
   to an unguarded default.
5. **Traceability.** `decisions.model` and `llm_calls.model` store the **resolved** model
   string, not the tier name. The price table (`FITME_PRICES_FILE`) must have an entry for
   every configured model. If one is missing, `/system` shows "cost unknown" for that model,
   and startup logs a warning.
6. **Per-agent model settings** (for example reasoning effort or max output tokens) go in
   the same dict in `llm/models.py`, as pydantic-ai `ModelSettings`. Output-retry budgets live in a sibling dict, `AGENT_OUTPUT_RETRIES`, because `retries` is an `Agent(...)` argument, not a `ModelSettings` key: 3 for plan_generate, plan_revise, session_adjust and plan_import; 2 for recap and assistant. An **output-validation** failure on the normal tier counts as a failed attempt and gets the one large-tier attempt. Provider errors do not. Look up the exact
   provider-specific keys in the pydantic-ai docs when implementing. Don't guess them.
7. **Pick tiers with data.** `fitme llm eval` (manual, spends real money, never in CI) runs
   each agent over the fixture profiles in `tests/fixtures/llm_eval/` on a given model and
   reports:
   - guard pass rate;
   - refusal rate;
   - tokens and estimated cost per call.

   Use it before moving an agent to a cheaper tier. Also compare against the simpler
   option: the same larger model at lower effort can match a cheaper model's cost with
   better quality.

### 9.2 Session & security

- Cookie `__Host-fitme_session`: `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`. The value
  is 32 random bytes (base64url). The DB stores only its SHA-256.
- Sessions have a 14-day idle expiry and a 30-day absolute expiry. `last_seen_at` is
  updated at most once per 5 minutes.
- CSRF: every POST form carries an HMAC token bound to the session (`FITME_SECRET_KEY`).
  Reject requests where it is missing or wrong.
- Headers: `Content-Security-Policy: default-src 'self'` (no inline script),
  `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`,
  `X-Frame-Options: DENY`.
- `/app/*` and `/api/*` need a valid session (dependency `require_user`).
- Web language: the user's `language`. On the login page, use `Accept-Language`.

### 9.3 Front-end conventions

- One CSS file with system fonts. It must work at phone width. Prefer semantic HTML.
- JS only where it helps: charts, form conveniences, confirm dialogs. Use ES modules with
  no bundler.
- Pages must work without JS, except charts, which fall back to a table.

### 9.4 Deleting training logs

This exists to remove test runs and mistakes. It is a **hard delete** with no undo. The
confirm page says so and links to the export.

Session and check-in ids use `AUTOINCREMENT` (migration 0005), so a deleted id is never reused. Decisions reference sessions by id inside JSON, and a reused id would inherit a deleted session's history.

What is deleted, in one transaction (`services/training.py::delete_sessions` →
`controllers.training.delete_sessions(conn, user_id, session_ids)`):

- the `workout_sessions` rows (only the user's own; any id that is not theirs aborts the
  whole request);
- their `set_logs` (`ON DELETE CASCADE`);
- `chat_messages` tied to those sessions.

What is **kept**, because the safety guards rely on it:

- **`health_holds`**: they are detached (`source_session_id → NULL`), not deleted. Deleting
  a halted session does **not** clear the hold. Holds clear only through their own flow
  (§6.6).
- **`checkins` with an answer other than `fine`**: they are detached, not deleted, so an
  unknown/worse/pain check-in keeps blocking increases until a newer check-in replaces it.
  `fine` check-ins for those sessions are deleted.
- **`decisions` / `decision_outcomes`**: append-only. The weekly increment cap reads from
  here (§7), so deleting logs can't unlock a second increase in the same week. They are
  removed only by a full account delete (§8.3).

Effects to expect:

- The historical max and load-engine history are recalculated from the remaining
  `set_logs`. Deleting a session can only **lower** the ceiling, which is the conservative
  direction. If every session for an exercise is deleted, the next session is calibration
  again.
- An `in_progress` session can be deleted. It is treated as aborted first.
- Each delete writes one `decision(kind=session_delete)`. Its `user_report` holds the
  deleted session ids, dates, workout keys and set counts. It does not hold a copy of the
  set data.

Bot: out of scope for v1. It can be added later as a **Delete** button on a finished
session's recap, using the same service.

## 10. Observability

- Structured logs (stdlib `logging`, JSON formatter) go to stdout/journald. **Never** log
  message text, health values or Telegram ids at INFO level. Log ids and event names.
- Use no external telemetry, crash reporting or analytics (AGENTS.md §1, §5). `fitme serve`
  and the systemd unit set `PYDANTIC_AI_NO_BANNER=1`, which suppresses pydantic-ai's
  promotional startup banner.
- `/system` and `fitme stats` cover operational visibility.

## 12. Language & copy rules (summary of AGENTS.md §3)

- Call it a training plan generator, training log or assistant. Never trainer, coach,
  physio, nutritionist, doctor, or "your personal X".
- Make no disease, diagnosis, treatment or weight-loss claims.
- Show the AI disclosure in `/start`, `/help`, the web footer and the README.
- The bot is plan-first with buttons and a small dialog for adjustments. It has no
  companion persona and no small talk.

## 13. Out of scope (v1)

Multi-user, invites or waiting list, payments, WhatsApp, calorie or bodyweight tracking,
reminders or notifications, a native app, and wearable integrations. Each of these either
changes the posture (AGENTS.md §8) or needs its own design pass with the guards from
AGENTS.md §4.
