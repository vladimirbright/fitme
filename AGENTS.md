# AGENTS.md

Operating guidance for coding agents working on this repository.

## 1. Project posture (read this first)

This is a **personal, self-hosted, non-commercial** training assistant. It is published as
open source so that other people can run their own instance. It is **not** a hosted service.

This posture is a hard constraint, not a temporary state. It is what keeps the project
outside GDPR controller obligations (household/personal-use exemption) and outside the EU
Product Liability Directive (which excludes free and open-source software developed and
supplied outside commercial activity).

**Do not implement any of the following without an explicit instruction that the posture has
changed:**

- public sign-up, invite links, or any onboarding for users the operator does not know
- a hosted multi-tenant deployment (one database serving strangers)
- payments, subscriptions, paywalls, usage metering for billing
- telemetry, crash reporting, or analytics that leaves the operator's own infrastructure

If a requested feature implies one of these, stop and say so before writing code. These are
business decisions with legal consequences (company formation, insurance, a DPIA), not
implementation details.

## 2. Safety rules for training output

The system tells a human being how much weight to lift. Treat these as invariants enforced in
code, not as prompt suggestions. A prompt can be ignored by the model; a guard cannot.

- **Progression cap.** Never propose an increment above the configured per-exercise maximum
  (default 2.5 kg per week for compound lifts). Reject model output that exceeds it.
- **Ceiling on absolute load.** Never propose a working weight above the user's logged
  historical maximum for that exercise plus one increment. If there is no history, the first
  session is data collection, not progression.
- **Silence is not consent.** If a check-in question ("how did the back feel?") goes
  unanswered, treat it as unknown, not as "fine". Unknown blocks a load increase.
- **Stop words halt the session.** Reported pain (not soreness), dizziness, numbness, chest
  discomfort, or a "something popped" event must stop plan generation for that session and
  emit a plain-language recommendation to see a doctor. No workaround, no "lighter
  alternative" — stop.
- **Refusal is a valid output.** The plan generator must be able to return "no plan" with a
  reason. If the only available path is to always return something, the design is wrong.
- **Screening before first plan.** Ask about injuries, contraindications, and relevant
  conditions once, at setup. Store the answers as flags that gate exercise selection, not as
  free text fed into a prompt.

## 3. Language rules

These apply to UI copy, README, system prompts, commit messages, and anything user-visible.

- Never describe the system as a trainer, coach, physiotherapist, nutritionist, doctor, or
  "your personal X". Acceptable framings: training log, plan generator, assistant.
- Never claim to diagnose, treat, prevent, manage, or monitor any disease or condition.
  Disease claims are what turn a wellness tool into a regulated medical device — in both the
  EU (MDR: intended purpose decides classification) and the US (FDA general wellness policy).
- Never present model output as equivalent to a licensed professional's advice.
- State clearly that plans are generated by AI. This is a standing requirement under EU AI Act
  Art. 50 for systems that interact with people, and it is cheap to satisfy: one line in the
  UI and one in the README.
- No claims about weight loss outcomes, body composition targets, or timelines.

## 4. Eating-disorder and vulnerable-user guards

If calorie or bodyweight tracking is implemented:

- Enforce a hard floor on any suggested calorie target. Refuse to generate targets below it.
- Refuse to set bodyweight goals below a healthy range for the user's height.
- Detect and refuse: rapid-loss requests, repeated goal lowering, obsessive re-querying of the
  same metric.
- Do not implement streaks, shame mechanics, or notifications that punish a missed day.
- Under-18 users are out of scope. Do not build flows for them.

## 5. Data architecture

Even in personal-use posture, build as if the data were regulated. It costs almost nothing now
and is very expensive to retrofit.

- **Separate tables, separate concerns:** identity (telegram_id, display name) apart from
  health metrics (weight, logs, self-reports) apart from derived output (plans, insights).
- **Pseudonymize prompts.** What goes to the LLM provider is `user 47, 41y, 125kg, history:
  [...]`. Never a name, never a telegram_id, never a chat handle.
- **Minimize at the schema level.** Store age, not date of birth, unless date of birth is
  actually used. If a column is not read by any code path, delete the column.
- **Export and delete from day one.** A single command that dumps everything for one user as
  JSON, and a single command that removes them entirely. These are ten lines each now and a
  refactor later.
- **Retention.** Raw chat messages: bounded TTL (default 365 days). Structured training log:
  keep. Do not keep raw text forever because it "might be useful".
- **No third-party ad or analytics SDKs anywhere near health data.** Not Meta, not Google Ads,
  not TikTok. If observability is needed, self-host it.
- **Secrets and DB credentials** never in the repo. The reference deployment must work with
  environment variables only.

## 6. Decision logging

Every generated plan and every in-session adjustment writes an immutable record containing:

- prompt template version and model identifier
- what the user reported (sets, weights, reps, subjective state)
- what the system proposed
- what the user actually did
- which guards fired, if any

This is primarily a debugging and product-quality tool. It is also the record that
demonstrates the system behaved conservatively, should that ever matter.

## 7. Interface and platform choices

- **Telegram Bot API is the interface.** Plan-first: the user sees a structured plan with
  checkboxes, with a small dialog for adjustments. Do not build a chat-first, companion-style
  persona. This is deliberate — anthropomorphic companion bots attract a body of regulation
  (age estimation, emotional-dependency safeguards, annual reporting under laws like
  Colorado's Chatbot Safety Act) that a plan-with-dialog interface does not.
- **Do not add WhatsApp.** Its Business API bills per message, and as of 1 October 2026
  in-window service messages are billable beyond a small monthly free allowance per number.
  A daily-use logging bot is the worst possible fit for that pricing model.
- **If payments are ever added** (see §1 — they are not, currently): use an external checkout
  with a merchant of record, not Telegram Stars. Stars lose roughly 32% on mobile purchases to
  app-store fees and pay out in crypto via Fragment, which is an accounting problem for an
  EU-registered entity.

## 8. What flips the posture

Any one of these means §1 no longer holds and the project needs real legal setup before
shipping:

- a second person's data lands on infrastructure the operator controls
- anyone can register without the operator personally granting access
- money changes hands
- the project is marketed, rather than merely published

When an agent sees a task heading in one of those directions, raise it rather than
implementing it.

## 9. Style

- Python. Type hints on public functions. No clever metaprogramming.
- Guards live in a dedicated module with unit tests. Every rule in §2 has a test that proves
  it blocks the bad case.
- Prompts live in version-controlled files, not inline strings.
- Prefer boring dependencies. This is a project meant to be readable by the person running it.
